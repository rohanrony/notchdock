Read Swift concurrency settings before claiming thread safety

Swift concurrency tools can help express isolation and asynchronous work, but their presence does not prove that an entire app has no data races or UI stalls. Start by checking the compiler mode and then follow each task’s data flow.

Check the project’s language mode first

The reviewed Xcode project sets SWIFT_VERSION = 5.0. It contains asynchronous tasks, but this is not evidence that the project compiles in Swift 6 language mode or enables strict-concurrency checking for every target. Inspect the target’s Build Settings before describing its concurrency guarantees.

Trace one async operation end to end

  1. Find where the task starts and what owns its lifetime. An unstructured Task needs an explicit cancellation or replacement plan.
  2. Follow values captured by the closure and the result returned after each await.
  3. Identify which actor or executor owns UI state and where the result updates that state.
  4. Check whether cancellation is tested before expensive or stale work continues.

Swift’s model uses actor isolation to control access to shared mutable state. Task cancellation is cooperative: calling cancel() signals cancellation, but the running operation must check and respond. See the Swift guide to concurrency and Apple’s Task documentation.

What a clean build does and does not prove

Compiler diagnostics can catch some issues under the project’s selected settings. They do not prove that runtime work is canceled at the right time, that every state transition is on the intended actor, or that animations have a measured frame rate. Keep build settings, code review, runtime traces, and user-visible performance claims separate.
